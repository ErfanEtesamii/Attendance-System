# مانیتورینگ و هشدار (بخش ۲-ج۱)

هدف: اگر چیزی در سرور خراب شد (بات قطع، Job شکست، دیسک پر، دیتابیس خطا)، ادمین‌ها **قبل از شکایت کارمندان** در تلگرام باخبر شوند.

## اجزا

| جزء | فایل | کار |
|---|---|---|
| ثبت اجرای Jobها | `src/utils/jobRunner.js`، جدول `job_runs` | هر Job زمان‌بندی‌شده با `wrapJob` اجرا می‌شود؛ شروع/پایان/موفق یا خطا/مدت ثبت می‌شود. خطای Job هرگز callback cron را نمی‌شکند؛ خطای دیتابیس هنگام ثبت هم Job را مختل نمی‌کند. |
| نبض polling بات | `src/utils/botHealth.js` | متد `bot.getUpdates` پیچیده می‌شود تا آخرین موفقیت/خطای **واقعی** long-poll معلوم باشد (نه صرفاً «پروسه زنده است»). |
| بررسی سلامت | `src/utils/systemHealth.js` | یک تابع واحد: دیتابیس (نوشتن/خواندن آزمایشی؛ `?deep=1` ⇒ `PRAGMA quick_check`)، polling بات، فضای آزاد دیسک، سن آخرین بک‌آپ، شکست Jobها. |
| Watchdog | `src/bot/scheduler/watchdog.js` | هر ۵ دقیقه (`CRON_WATCHDOG`) بررسی می‌کند و به ادمین‌های فعال (نقش `admin` با آیدی تلگرام) هشدار می‌دهد. |
| `GET /api/health` | `src/api/routes/health.js` | **عمومی**: فقط `{status: "ok"|"degraded", time}`، ۱۰ ثانیه کش، همیشه HTTP ۲۰۰ (مصرف‌کننده باید فیلد `status` را بخواند). |
| `GET /api/admin/system/status` | `src/api/routes/admin/system.js` | **فقط ادمین کل**: همه‌ی جزئیات + فهرست Jobها + آخرین خطاها + هشدارهای فعال. |
| صفحه‌ی «وضعیت سیستم» | `public-admin/js/views-admin.js` | منوی «مدیریت» (فقط ادمین). |

## نوع‌های هشدار

| کلید | شرط | رفع |
|---|---|---|
| `db_error` | نوشتن/خواندن آزمایشی دیتابیس شکست خورد | خودکار با برگشتن |
| `bot_polling` | بیش از `MONITOR_POLLING_STALE_SECONDS` (پیش‌فرض ۱۲۰) از آخرین `getUpdates` موفق گذشته | خودکار |
| `disk_low` | فضای آزاد دیسکِ پوشه‌ی دیتابیس < `MONITOR_DISK_MIN_FREE_MB` (پیش‌فرض ۱۰۲۴) | خودکار |
| `backup_stale` | **فقط اگر `MONITOR_BACKUP_CHECK=true`**: آخرین بک‌آپ (غیر `pre-migration-*`) قدیمی‌تر از `MONITOR_BACKUP_MAX_AGE_HOURS` (۳۶) یا ناموجود | خودکار |
| `backup_suspect` | **فقط اگر `MONITOR_BACKUP_CHECK=true`**: فایل `daily-….db.suspect` وجود دارد که **جدیدتر از آخرین بک‌آپ سالم** است (بک‌آپ تازه `PRAGMA integrity_check` را رد کرد؛ S2-1c) | خودکار با اولین بک‌آپ سالمِ بعدی (خودِ فایل `.suspect` پاک نمی‌شود) |
| `job_failed:<نام>` | آخرین نتیجه‌ی Job «خطا» بوده و کمتر از `MONITOR_JOB_FAILURE_WINDOW_HOURS` (۷۲) گذشته | با اولین اجرای موفق بعدی همان Job |

## قواعد ارسال (throttle)

- مشکل تازه ⇒ **فوراً** هشدار.
- ادامه‌ی مشکل ⇒ حداکثر یک هشدار از هر نوع در هر `ALERT_THROTTLE_MINUTES` (پیش‌فرض ۶۰). استثنا: `job_failed` و `backup_suspect` هر ۲۴ ساعت (Jobهای هفتگی/ماهانه تا اجرای بعدی «شکست‌خورده» می‌مانند و هشدار ساعتی مزاحم می‌شد).
- رفع مشکل ⇒ یک پیام «✅ رفع شد»، بعد سکوت.
- هشدار فقط وقتی «ارسال‌شده» ثبت می‌شود که **حداقل یک ادمین** پیام را گرفته باشد؛ وگرنه چرخه‌ی بعد دوباره تلاش می‌کند.
- وضعیت هشدارها در جدول `monitor_alerts` است (با ری‌استارت گم نمی‌شود). اگر خودِ دیتابیس خراب باشد، `db_error` با وضعیت حافظه و آخرین فهرست شناخته‌شده‌ی ادمین‌ها یک‌بار ارسال می‌شود.
- متن هشدار و `job_runs.error` از `sanitizeText` رد می‌شوند: توکن بات (که گاهی داخل URL خطای شبکه می‌آید) حذف می‌شود.

## بک‌آپ سالم و فایل‌های `.suspect` (S2-1c)

- «آخرین بک‌آپ» در `systemHealth` (`checks.backup.lastBackupAt/lastBackupFile`) همیشه **آخرین بک‌آپ سالم** است: فقط فایل‌هایی که با نام نهایی (`daily-….db`، `monthly-….db`) منتشر شده‌اند، یعنی `integrity_check` را رد کرده‌اند. `.suspect`، `.partial` و `pre-migration-*` هرگز حساب نمی‌شوند.
- `checks.backup.suspect` فقط وقتی پر است که یک `.suspect` **جدیدتر از آخرین بک‌آپ سالم** وجود داشته باشد؛ در این حالت `checks.backup.ok=false` و وضعیت کلی `degraded` می‌شود (`stale` جداگانه می‌گوید بک‌آپ سالم از نظر سن هم قدیمی است یا نه).
- اگر هم‌زمان Job `dailyBackup` با خطای integrity ثبت شود، دو هشدار می‌آید: `backup_suspect` (با نام فایل و آخرین بک‌آپ سالم) و `job_failed:dailyBackup` (متن خطا). هر دو با اولین بک‌آپ سالمِ بعدی خودکار «رفع شد» می‌شوند.
- فایل `.suspect` را **دستی** بررسی/پاک کنید؛ retention به آن دست نمی‌زند. صفحه‌ی «وضعیت سیستم» هم ردیف «فایل بک‌آپ مشکوک» را نشان می‌دهد.
- بعد از اولین استقرار با پیش‌فرض `true`، تا وقتی اولین بک‌آپ روزانه ساخته نشده (`CRON_DAILY_BACKUP`، پیش‌فرض ۰۲:۳۰) هشدار «هیچ بک‌آپ سالمی پیدا نشد» می‌آید؛ برای جلوگیری، یک‌بار بک‌آپ را دستی اجرا کنید یا موقتاً `MONITOR_BACKUP_CHECK=false` بگذارید.

## تنظیمات (`.env`)

| متغیر | پیش‌فرض |
|---|---|
| `WATCHDOG_ENABLED` | `true` (`false` ⇒ خاموش) |
| `CRON_WATCHDOG` | `*/5 * * * *` |
| `ALERT_THROTTLE_MINUTES` | `60` |
| `MONITOR_DISK_MIN_FREE_MB` | `1024` |
| `MONITOR_POLLING_STALE_SECONDS` | `120` |
| `MONITOR_JOB_FAILURE_WINDOW_HOURS` | `72` |
| `MONITOR_BACKUP_CHECK` | `true` (از S2-1c؛ فقط مقدار `false` خاموشش می‌کند) |
| `BACKUP_DIR` | `./data/backups` |
| `MONITOR_BACKUP_MAX_AGE_HOURS` | `36` |

## محدودیت‌های صادقانه

- Watchdog **داخل همان پروسه‌ی Node** اجرا می‌شود. اگر کل پروسه/سرویس بمیرد (NSSM متوقف، سرور خاموش)، هیچ هشداری نمی‌رود. برای این حالت یک پایشگر **بیرون از سرور** لازم است (مثلاً یک سرویس مثل UptimeRobot/Uptime Kuma روی دستگاه دیگر که `https://…/api/health` را می‌پرسد و روی `status !== "ok"` یا نبودن پاسخ هشدار می‌دهد). NSSM خودش سرویس را بعد از crash دوباره بالا می‌آورد (`AppExit Default Restart`)؛ آن را بررسی کنید.
- «Job اجرا نشد» (cron اصلاً فعال نشد) تشخیص داده نمی‌شود؛ فقط «Job اجرا شد و شکست خورد». (برای تشخیص اجرای جاافتاده باید زمان مورد انتظار هر عبارت cron محاسبه شود؛ عمداً فعلاً نیامده.)
- هشدار از طریق همان بات تلگرام می‌رود؛ اگر مشکل خودِ دسترسی به Telegram API باشد (اینترنت قطع)، هشدار `bot_polling` ثبت می‌شود ولی **نمی‌تواند برسد** تا اینترنت برگردد؛ صفحه‌ی «وضعیت سیستم» و `/api/health` همچنان وضعیت را نشان می‌دهند.
- `job_runs` فعلاً پاک‌سازی دوره‌ای ندارد (حدود ۱۰۰ ردیف در روز)؛ سیاست نگهداری در ۲-د (چرخه‌ی عمر داده) می‌آید.
- فضای دیسک با `fs.statfsSync` (Node ≥ 18.15) اندازه‌گیری می‌شود؛ اگر پشتیبانی نشود بررسی «اعمال‌نشدنی» می‌شود، نه خراب.
- فقط‌-API (`npm run start:api-only`): بات و Jobها اجرا نمی‌شوند؛ بررسی polling «اعمال‌نشدنی» است و Jobها چیزی ثبت نمی‌کنند.
