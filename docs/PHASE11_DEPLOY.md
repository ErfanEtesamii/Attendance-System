# فاز ۱۱ — استقرار و چک‌لیست تست دستی

تصمیم‌ها و فرض‌ها: [`PHASE11_DECISIONS.md`](PHASE11_DECISIONS.md).

## ۱. پیش از استقرار (روی سیستم توسعه)

```powershell
npm install
npm test
npm run smoke
npm run secret-scan
```

هر سه باید سبز باشند (`secret-scan` کد خروج ۰ = بدون یافته). سپس `npm run package` برای zip تحویل بدون `.env`/`data`/`node_modules`.

## ۲. استقرار روی سرور (PowerShell، Administrator)

> یک بک‌آپ دستی از `data\attendance.db` بگیرید (`npm run migrate` هم پیش از اعمال، بک‌آپ سازگار با WAL می‌گیرد).

```powershell
cd "C:\path\to\Attendance System"
.\deploy\nssm.exe stop FarazHonarAttendance
Copy-Item data\attendance.db "data\backups\pre-phase11-$(Get-Date -Format yyyyMMdd-HHmm).db"
# جایگزینی کد (بدون دست‌زدن به .env و data\ و .ssl\)
npm install
npm run migrate                            # اعمال ۰۲۷
npm run migrate:status                     # همه باید applied باشند
.\deploy\nssm.exe start FarazHonarAttendance
```

- فقط یک migration تازه دارد: `027_dispute_messages` (افزایشی و idempotent؛ پیام اولیه‌ی اعتراض‌های قدیمی را به thread کپی می‌کند).
- متغیر `.env` جدید ندارد.
- تنظیم تازه در پنل: `disputeMaxReopens` (پیش‌فرض ۳؛ ۰ = ادامه‌ی اعتراض خاموش).
- فایل `nssm.exe` باید در `deploy\` باشد (در مخزن نیست؛ اسکریپت‌های `.bat`/`install-service.ps1` همان سرویس `FarazHonarAttendance` را می‌سازند).
- **تغییر رفتار برای کاربران:** برنامه‌ی هفته‌ی شروع‌شده دیگر قابل ویرایش نیست؛ تسک low مانع خروج نیست. گیت‌ها همچنان طبق `planGateMode` / `dailyReportGateMode` تنظیم می‌شوند.

## ۳. چک‌لیست تست دستی (نسخه‌ی تست، تلگرام واقعی)

به ترتیب:

1. **ثبت برنامه با اولویت‌های مختلف:** Mini App ⇒ برنامه‌ی هفته‌ی بعد؛ کارت هر روز؛ تسک‌هایی با اولویت بالا، عادی و کم؛ نشان رنگی و متن اولویت دیده شود؛ بدون اسکرول افقی روی عرض موبایل؛ ثبت نهایی.
2. **خروج با تسک normal انجام‌نشده (مسدود):** `dailyReportGateMode=enforce`؛ خروج بدون پاسخ به تسک normal ⇒ ۴۰۹ با پیام فارسی که عنوان را می‌گوید. با «انجام نشد + علت» خروج آزاد شود.
3. **خروج با تسک low (آزاد):** فقط تسک low پاسخ‌نشده ⇒ خروج بدون مانع؛ در ویزارد با برچسب «اختیاری»؛ پاسخ دادن به آن هم ذخیره شود و گزارش شبانه سرپرست «گزارش نداده» ننویسد.
4. **ویرایش هفته‌ی شروع‌شده (رد):** برنامه‌ی هفته‌ی جاری فقط‌خواندنی با پیام «هفته شروع شده…»؛ تلاش مستقیم API ⇒ ۴۰۹ `PLAN_LOCKED`؛ هفته‌ی آینده همچنان ویرایش‌پذیر.
5. **اعتراض با چند پیام:** کارمند اعتراض ثبت کند ⇒ ادمین از پنل (`#/disputes/<id>`) پاسخ بدهد ⇒ کارمند اعلان تلگرام بگیرد و پاسخ را در «اعتراض‌های من» ببیند ⇒ کارمند پیام دوم بدهد ⇒ ادمین اعلان پنل بگیرد.
6. **ادامه و خاتمه:** ادمین resolve کند ⇒ کارمند «ادامه‌ی اعتراض» با پیام جدید (تا سقف `disputeMaxReopens`؛ بعد از سقف ۴۰۹) ⇒ «مشکلم حل شد، خاتمه» با تأیید ⇒ دیگر پیام نپذیرد.
7. **بستن ماه:** اعتراض باز مانع بستن ماه باشد؛ حل‌شده یا خاتمه‌یافته توسط کارمند مانع نباشد؛ در ماه بسته پیام/ادامه/خاتمه ⇒ `MONTH_CLOSED`.
8. **اعتراض قدیمی:** اعتراضی که پیش از migration ثبت شده، پیام اولیه‌اش را در thread نشان دهد.
9. **مرور UI:** عرض ۳۲۰px، RTL، تم روشن/تیره، خوانشگر برای نمای برنامه‌ی هفتگی و گفت‌وگوی اعتراض.

## ۴. بازگشت (Rollback)
`.\deploy\nssm.exe stop FarazHonarAttendance` ← بازگردانی کد قبلی و بک‌آپ `pre-phase11-*.db` (طبق `BACKUP_RESTORE.md`) ← `.\deploy\nssm.exe start FarazHonarAttendance`. migration ۰۲۷ فقط ستون/جدول اضافه می‌کند و کد فاز ۱۰ با آن کار می‌کند، ولی بازگردانی بک‌آپ تمیزترین مسیر است.
